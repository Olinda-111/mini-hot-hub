# 多平台热搜聚合网站 · 产品需求文档

---

## 摘要

本项目拟构建一个用户可自定义的多平台热搜聚合网站。首次访问默认展示微博、知乎、B 站三大平台的热搜榜单；用户可通过平台选择器增减关注的平台，页面布局根据所选平台数量自动调整，偏好设置通过浏览器本地存储持久化。区别于现有竞品固定平台列表的做法，本项目的核心差异化在于赋予用户对信息源的主动管理权。本文档从产品概述、目标用户、核心功能、界面设计及技术选型五个维度，系统阐述产品的需求定义与设计约束。

**关键词**：热搜聚合；平台注册表；用户自定义；动态布局；React；Express

---

## 1. 产品概述

### 1.1 产品定位

一个**用户可自定义**的多平台热搜聚合网站。核心设计原则：默认精简，按需扩展——首次访问展示微博、知乎、B 站三个默认平台，用户可按自身需求增减，页面无需刷新即可适应。

### 1.2 产品形态

- **类型**：单页 Web 应用（SPA）
- **访问方式**：浏览器直接访问，无需安装客户端，无需登录
- **数据来源**：各平台公开 JSON API，后端代理请求并统一格式化
- **偏好持久化**：浏览器 localStorage，无需服务端存储

### 1.3 核心价值主张

| 维度           | 说明                                                           |
| -------------- | -------------------------------------------------------------- |
| 用户自定义     | 从平台注册表中选择关注的平台，而非被动接受预设列表               |
| 偏好持久化     | 一次设置长期有效，下次访问自动恢复                               |
| 动态布局       | 页面根据所选平台数量自动调整卡片网格，不浪费屏幕空间             |
| 一站式浏览     | 单一页面呈现所选全部平台热搜，无需逐个打开 App                   |
| 干净无广告     | 仅展示标题与链接，无商业广告、无算法推荐、无弹窗                  |
| 原生跳转       | 点击标题直接跳转源平台，不经过中间页，不做流量劫持                |

## 2. 目标用户

### 2.1 主要用户群体

| 用户类型                 | 特征描述                                           | 自定义需求                                       |
| ------------------------ | -------------------------------------------------- | ------------------------------------------------ |
| 普通网民（上班族、学生） | 希望快速浏览各平台热点                             | 只看常用 2–3 个平台，减少无关信息干扰              |
| 自媒体与内容创作者       | 跨平台追踪热点选题，了解不同平台的话题差异          | 根据当天选题方向灵活增删平台                     |
| 全栈开发学习者           | 对 Vibe Coding / 全栈开发感兴趣                     | 了解平台注册表模式、动态路由、localStorage 持久化   |

### 2.2 用户需求分析

目标用户的核心诉求可归纳为四点：

1. **效率需求**：在单一页面内完成跨平台热搜浏览，降低信息获取的时间成本。
2. **个性化需求**：不同用户关心的平台不同，系统应允许用户自主选择信息源。
3. **信息全面性需求**：避免被单一平台算法裹挟，获取更全面的舆论图景。
4. **学习需求**：通过一个完整的全栈项目理解前后端协作、API 代理、缓存策略等工程实践。

## 3. 核心功能

### 3.1 最小可行产品

#### 3.1.1 平台注册表

系统维护一份平台注册表（Platform Registry），定义所有后端可获取数据的平台。注册表由后端管理，前端通过 API 获取元数据。

注册表结构：

| 字段          | 类型      | 说明                             | 示例               |
| ------------- | --------- | -------------------------------- | ------------------ |
| `id`          | `string`  | 平台唯一标识                     | `"weibo"`          |
| `name`        | `string`  | 展示名称                         | `"微博热搜"`        |
| `icon`        | `string`  | 平台图标（emoji）                 | `"🔥"`             |
| `color`       | `string`  | 品牌主题色（hex）                 | `"#e6162d"`        |
| `description` | `string`  | 平台简介，在选择面板中展示         | `"新浪微博实时热搜榜"` |
| `enabled`     | `boolean` | 是否在默认选择中                   | `true`             |

MVP 阶段注册表内容：

| id         | name       | icon | color     | enabled | 说明               |
| ---------- | ---------- | ---- | --------- | ------- | ------------------ |
| `weibo`    | 微博热搜   | 🔥   | `#e6162d` | true    | 默认启用           |
| `zhihu`    | 知乎热榜   | 💡   | `#0066ff` | true    | 默认启用           |
| `bilibili` | B 站热搜   | 📺   | `#fb7299` | true    | 默认启用           |

后续迭代时，新增平台仅需在注册表中追加条目并实现对应的 fetch 函数。

#### 3.1.2 平台选择器（Platform Selector）

页面顶部或侧边提供平台管理入口，交互逻辑如下：

1. **入口**：页面头部固定位置显示「管理平台」按钮（或齿轮图标 ⚙️）
2. **面板**：点击后弹出下拉面板或右侧抽屉，展示注册表中所有平台
3. **展示**：每个平台显示图标、名称、简介，以及一个勾选框
4. **勾选行为**：
   - 勾选 → 立即在页面上增加该平台的卡片，卡片以动画渐入
   - 取消勾选 → 卡片以动画渐出后移除
   - 至少保留 1 个平台（最后一个不可取消）
5. **关闭**：点击面板外部区域或关闭按钮收起面板
6. **持久化**：每次勾选/取消操作立即写入 `localStorage`

**设计说明**：原稿中平台数量固定为 3，本方案升级为动态可选。选择器交互参考 RSS 阅读器的订阅源管理，但更简化——仅需勾选预定义的平台，无需用户配置 URL 或 API 端点。

#### 3.1.3 动态卡片网格

页面主体区域以卡片网格展示当前选中平台的热搜榜单。布局规则如下：

- **列数自适应**：使用 CSS Grid 的 `auto-fill` + `minmax(320px, 1fr)`，浏览器自动计算最优列数
- **最小卡片宽度**：320px，确保每条热搜标题有足够展示空间
- **间距**：卡片之间 20px 间距
- **加载状态**：各卡片独立展示加载动画（骨架屏），互不阻塞
- **空状态**：若用户取消所有平台，展示引导文案"请选择至少一个平台"

响应式表现：

| 视口宽度     | 1 个平台 | 2 个平台 | 3 个平台 | 4+ 个平台       |
| ------------ | -------- | -------- | -------- | --------------- |
| `> 1000px`   | 1 列     | 2 列     | 3 列     | auto-fill（最多约 3 列） |
| `640–1000px` | 1 列     | 2 列     | 2 列     | auto-fill（最多约 2 列） |
| `< 640px`    | 1 列     | 1 列     | 1 列     | 1 列            |

#### 3.1.4 热搜卡片内容

每张卡片包含以下元素：

| 区域     | 内容                                                         |
| -------- | ------------------------------------------------------------ |
| 卡片头部 | 平台图标 + 平台名称 + 品牌色顶部强调条                          |
| 榜单列表 | 默认展示 Top 10，点击「展开」显示 Top 15（纯前端截断，不额外请求） |
| 单条内容 | 排名徽章（前 3 名金/银/铜色） + 可点击标题 + 热度值             |
| 卡片底部 | 数据更新时间，格式为「更新于 × 分钟前」                        |
| 错误状态 | 若该平台数据获取失败，卡片内显示友好提示文案                     |

每条热搜条目数据字段：

| 字段    | 类型             | 说明                           | 必填 |
| ------- | ---------------- | ------------------------------ | ---- |
| `rank`  | `number`         | 排名序号（从 1 开始）           | 是   |
| `title` | `string`         | 热搜标题                        | 是   |
| `url`   | `string`         | 跳转至源平台的完整链接（新标签页） | 是   |
| `heat`  | `number\|string` | 热度值，前端统一格式化后展示     | 否   |

#### 3.1.5 数据接口

自建后端服务提供以下 API 路由：

| 路由                           | 方法 | 优先级 | 说明                                                         |
| ------------------------------ | ---- | ------ | ------------------------------------------------------------ |
| `GET /api/platforms`           | GET  | P0     | 返回平台注册表元数据（不含 fetch 函数），供前端渲染选择器面板  |
| `GET /api/hot?platforms=a,b,c` | GET  | P0     | 按查询参数获取指定平台的热搜数据；缺省 `platforms` 时使用默认启用平台 |
| `GET /api/hot/:source`         | GET  | P1     | 按需获取单个平台数据，用于手动刷新单个卡片                      |

聚合响应格式（`GET /api/hot`）：

```typescript
{
  ok: boolean;
  cached: boolean;
  data: Platform[];
}
```

各平台数据来源与字段映射：

| 平台 | 数据源 API                                                               | `rank` 来源              | `title` 来源                 | `heat` 来源       | `url` 拼接规则                                  |
| ---- | ------------------------------------------------------------------------ | ------------------------ | ---------------------------- | ----------------- | ----------------------------------------------- |
| 微博 | `weibo.com/ajax/side/hotSearch`（需 Referer）                             | `data.realtime[].rank`   | `.word` 或 `.note`           | `.raw_hot`（数字） | `s.weibo.com/weibo?q={word}`                    |
| 知乎 | `zhihu.com/api/v3/feed/topstory/hot-lists/total?limit=50`（需 UA）       | 数组索引 + 1             | `.target.title`              | `.detail_text`（文本） | `.target.url`（相对路径需补全前缀）               |
| B 站 | `api.bilibili.com/x/web-interface/wbi/search/square?limit=50`            | 数组索引 + 1             | `.show_name` 或 `.keyword`   | `.heat_score`（数字） | `search.bilibili.com/all?keyword={keyword}`      |

#### 3.1.6 缓存机制

- 缓存键按平台组合生成，格式为 `"hot:{sorted_ids}"`，例如 `"hot:bilibili,weibo,zhihu"`
- 不同平台组合拥有独立的缓存条目，互不干扰
- TTL 设定为 **7 分钟**（`7 × 60 × 1000 ms`）
- 命中缓存时响应中 `cached` 字段为 `true`；未命中时并发请求，写入缓存后 `cached` 为 `false`
- 前端根据 `updatedAt` 时间戳展示「更新于 × 分钟前」
- 进程重启时缓存自动清空

#### 3.1.7 偏好持久化

- **存储位置**：浏览器 `localStorage`
- **存储键**：`"hot-site-platforms"`
- **存储格式**：逗号分隔的平台 ID，例如 `"weibo,zhihu,bilibili"`
- **写入时机**：用户每次在平台选择器中变更勾选状态时立即写入
- **读取时机**：页面初始化时读取，若为空则使用默认平台列表（`enabled: true` 的平台）
- **同步**：纯前端行为，不涉及后端接口

#### 3.1.8 异常处理

- 采用 `Promise.allSettled` 并发请求选中平台，单平台失败不影响其他平台
- 失败平台的卡片展示友好提示（如"数据获取失败，请稍后重试"）
- 若所有选中平台均请求失败，展示全局错误状态与「重试」按钮
- 后端每个 fetch 设置 8 秒超时（`AbortController`）
- 平台选择器面板内的平台列表获取失败时，降级为内置默认列表

#### 3.1.9 部署要求

- 源代码托管于 GitHub 公开仓库
- 生产环境通过 HTTPS 公网可访问，支持 Vercel / Railway 一键部署
- 开发环境：Vite dev server（端口 `5173`）通过 proxy 将 `/api` 代理至 Express 后端（端口 `3001`）

### 4.4 动态网格布局

采用 CSS Grid `auto-fill` + `minmax` 实现列数自适应：

```css
.grid {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(320px, 1fr));
  gap: 20px;
}
```

该方案的优势在于无需针对不同平台数量编写分支逻辑，浏览器根据容器宽度和最小卡片宽度自动计算列数。

## 5. 技术选型

### 5.1 技术栈

| 层级     | 技术方案          | 版本要求     |
| -------- | ----------------- | ------------ |
| 前端框架 | React             | React 18     |
| 类型系统 | TypeScript        | 按需引入      |
| 构建工具 | Vite              | Vite 5       |
| 样式方案 | 原生 CSS          | —            |
| 状态管理 | React useState + useEffect | — |
| 持久化   | localStorage      | 浏览器原生    |
| 后端框架 | Node.js + Express | Express 4    |
| 运行时   | Node.js           | >= 18（LTS） |
| 部署平台 | Vercel / Railway  | 不强制统一    |

### 5.2 选型说明

- **React**：成熟的组件化开发模式；平台选择器的状态管理、卡片列表的条件渲染天然适合 React 的单向数据流。
- **原生 CSS Grid `auto-fill`**：相比 JavaScript 动态计算列数的方案，CSS Grid 更简洁且性能更优，无需监听 resize 事件。
- **localStorage**：用户偏好数据量极小（仅一串平台 ID），无需引入 IndexedDB 或后端存储。读取为同步操作，组件初始化时即可获取。
- **Express**：后端仅需处理 API 路由和静态资源托管，无需全栈框架。
- **Vercel**：支持 Git 仓库连接后一键部署，自动 HTTPS，免费额度充足。

### 5.3 否决方案

| 否决方案                     | 理由                                                         |
| ---------------------------- | ------------------------------------------------------------ |
| Next.js                      | 纯客户端渲染的 SPA，不需要 SSR/SSG                             |
| 数据库（MySQL / MongoDB）    | 7 分钟缓存无持久化需求；用户偏好存 localStorage，无服务端存储需求 |
| Redux / Zustand 等状态管理库 | 全局状态仅"选中平台列表"一项，React 内置 useState + Context 完全够用 |
| CSS 框架（Tailwind / Bootstrap） | 样式量约 400 行，手写 CSS 更灵活                              |
| 第三方热搜付费 API            | 多数收费或不稳定，直接调平台公开接口更可靠                      |

### 数据流

```
localStorage("hot-site-platforms")
       │
       ▼
App (useState: selectedPlatforms)
       │
       ├──▶ PlatformSelectorPanel（读写 selectedPlatforms）
       │        │
       │        └── onChange → setSelectedPlatforms → 写入 localStorage
       │
       └──▶ fetch(`/api/hot?platforms=${selectedPlatforms.join(",")}`)
                │
                ▼
            Express 后端
                │
                ├── 解析 platforms 查询参数
                ├── 检查缓存（key = "hot:{sorted_ids}"）
                ├── Promise.allSettled(选中平台的 fetch 函数)
                └── 返回 JSON
                │
                ▼
            Grid 渲染 PlatformCard × N
```
