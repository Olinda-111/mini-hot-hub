# 多平台热搜聚合网站 · 需求研究报告

---

## 摘要

本报告围绕"构建用户可自定义的多平台热搜聚合网站"这一命题，从产品定义、需求论证、竞品对比、技术可行性及风险评估五个维度展开系统研究。区别于现有竞品固定平台列表的做法，本项目核心差异化在于**允许用户自主选择关注的平台**，页面根据所选平台数量自动调整卡片布局，偏好设置通过浏览器本地存储持久化。研究表明，现有竞品均不支持用户自定义平台组合，该功能填补了市场空白。技术层面，平台注册表 + 动态路由 + 自适应网格的方案可行，各平台公开 JSON API 可稳定获取结构化数据。

**关键词**：热搜聚合；平台注册表；用户自定义；动态布局；React；Express

---

## 1. 研究目标与范围

### 1.1 研究问题

本报告旨在回答以下四个核心问题：

1. **要做什么**：产品功能边界、用户自定义平台的交互模型是什么？
2. **为什么要做**：固定平台列表的痛点是什么？自定义选择解决了什么问题？
3. **有没有人做过**：现有竞品是否支持用户自定义平台组合？差异化空间在哪里？
4. **技术上是否可行**：平台注册表架构、动态路由、自适应布局能否在 MVP 周期内实现？

### 1.2 研究范围

| 维度         | 范围                                                         |
| ------------ | ------------------------------------------------------------ |
| 平台覆盖     | 默认微博、知乎、B 站；预留扩展接口，后续逐步接入百度、头条等    |
| 用户自定义   | 从平台注册表中选择启用的平台；选择结果持久化至 localStorage      |
| 技术方案     | 后端平台注册表 → 动态路由接收平台参数 → 前端自适应网格渲染       |
| 竞品范围     | 直接竞品（多平台聚合网站）+ 间接竞品（单平台镜像 / RSS / App）   |
| 风险评估     | 技术风险（API 变更、限流）+ 法律合规风险                         |

### 1.3 研究方法

- **竞品分析**：横向对比 7 款产品，重点考察是否存在"用户自定义平台"功能
- **技术验证**：对各平台公开 API 进行实际调用测试，记录限制条件
- **需求推演**：基于竞品功能缺口推导差异化空间

## 2. 产品定义

### 2.1 产品形态

一个**用户可自定义**的多平台热搜聚合网站。首次访问默认展示微博、知乎、B 站三大平台；用户可通过平台选择器增减关注的平台，页面布局根据所选平台数量自动调整，选择结果持久化至浏览器本地存储，下次访问时自动恢复。

### 2.2 核心交互模型

```
首次访问 → 默认展示微博/知乎/B站（3 卡片）
              ↓
用户点击「管理平台」→ 弹出平台选择面板
              ↓
勾选/取消勾选平台 → 页面实时更新卡片
              ↓
选择结果自动保存至 localStorage
              ↓
下次访问 → 恢复上次选择的平台组合
```

### 2.3 数据字段定义

每条热搜条目统一包含以下字段：

| 字段    | 类型             | 说明                             | 必填 |
| ------- | ---------------- | -------------------------------- | ---- |
| `rank`  | `number`         | 排名序号（从 1 开始）             | 是   |
| `title` | `string`         | 热搜标题                          | 是   |
| `url`   | `string`         | 可直接跳转的源站链接               | 是   |
| `heat`  | `number\|string` | 热度值，各平台格式不同，前端统一格式化 | 否   |

### 2.4 平台注册表概念

系统维护一份**平台注册表**（Platform Registry），包含所有后端已实现数据获取逻辑的平台元信息。注册表中的每个条目包含：

| 字段          | 类型       | 说明                               | 示例                       |
| ------------- | ---------- | ---------------------------------- | -------------------------- |
| `id`          | `string`   | 平台唯一标识                       | `"weibo"`                  |
| `name`        | `string`   | 展示名称                           | `"微博热搜"`                |
| `icon`        | `string`   | 平台图标（emoji）                   | `"🔥"`                     |
| `color`       | `string`   | 品牌主题色                          | `"#e6162d"`                |
| `description` | `string`   | 平台简介，在选择面板中展示           | `"新浪微博实时热搜榜"`       |
| `enabled`     | `boolean`  | 是否默认启用                        | `true`                     |

用户的选择本质上是"从注册表中勾选一个子集"，而非创建新的数据源。新增平台需开发者先在注册表中注册对应的 fetch 函数，用户才能选择。

### 2.5 明确排除

- 不做用户自行配置 API 端点（安全风险，MVP 不做）
- 不做内容详情页、不做登录注册、不做收藏评论
- 不做服务端持久化用户偏好（使用 localStorage，零后端存储成本）

## 3. 需求论证

### 3.1 固定平台列表的痛点

现有所有热搜聚合产品的平台列表由产品方预设，用户无法调整。这带来以下问题：

1. **信息冗余**：用户可能只关心其中 2–3 个平台，但页面强制展示 8–20 个平台的卡片，导致信息过载。
2. **偏好无法持久化**：每次访问都需要重新在密集的布局中定位自己关心的平台。
3. **个性化缺失**：不同用户的平台偏好不同（有人只看微博+知乎，有人只看 B 站+百度），但产品不做区分。

### 3.2 自定义选择解决的核心问题

| 痛点                       | 本方案解决方式                                   |
| -------------------------- | ------------------------------------------------ |
| 信息冗余                   | 用户取消不需要的平台，页面只展示关心的内容         |
| 无法持久化偏好             | localStorage 自动保存/恢复，一次设置长期有效       |
| 布局浪费（3 列但有 5 个平台） | 动态网格根据平台数量自动调整列数                  |

### 3.3 需求验证

1. **竞品功能缺口**：经调研，`tophub.today`、`rebang.today`、`hot.opensns.cn` 等 7 款竞品均不支持用户自定义平台组合。该功能为市场空白。
2. **类比验证**：RSS 阅读器（如 Feedly、Inoreader）的"订阅源管理"模式已证明用户愿意主动管理信息来源，热搜聚合可借鉴该模式。
3. **本人即目标用户**：我日常关注的平台为微博和知乎，B 站偶尔看。固定展示所有平台不如按需选择。

### 3.4 目标用户画像

| 用户类型             | 特征描述                                           | 自定义平台的需求                                   |
| -------------------- | -------------------------------------------------- | -------------------------------------------------- |
| 普通网民             | 希望快速了解各平台热点                             | 只看常用 2–3 个平台，减少无关信息干扰                |
| 自媒体与内容创作者   | 跨平台追踪热点选题                                 | 根据当天选题方向灵活增删平台                       |
| 全栈开发学习者       | 以本项目为参考案例                                 | 了解平台注册表模式、动态路由、localStorage 持久化    |

## 4. 竞品分析

### 4.1 直接竞品

| 产品               | 覆盖平台数 | 用户可自定义平台 | 是否需要登录 | 广告 | 移动端适配 |
| ------------------ | ---------- | ---------------- | ------------ | ---- | ---------- |
| **tophub.today**   | 20+        | ❌ 不支持         | 否           | 无   | 一般       |
| **rebang.today**   | 8+         | ❌ 不支持         | 否           | 无   | 良好       |
| **hot.opensns.cn** | 10+        | ❌ 不支持         | 否           | 有   | 差         |
| 各平台官方热榜     | 1          | ❌ 不适用         | 部分需登录   | 有   | 参差不齐   |

### 4.2 间接竞品

| 产品                     | 类型         | 用户自定义能力           | 与本案的关系                             |
| ------------------------ | ------------ | ------------------------ | ---------------------------------------- |
| RSS 阅读器（Feedly 等）  | 订阅管理     | ✅ 用户自选订阅源         | 订阅管理模式可借鉴，但 RSS 阅读器门槛高     |
| 微博第三方热搜镜像站     | 单平台聚合   | ❌ 不支持               | 证明单平台聚合有需求，但无跨平台能力        |
| 今日热榜 App             | 移动端 App   | ❌ 不支持               | 体验好但 Web 端空白                       |

### 4.3 关键发现：用户自定义功能为市场空白

调研的 7 款直接/间接竞品中，**无一支持用户自定义平台组合**。所有产品均为预设平台列表，用户被动接受。RSS 阅读器的"自选订阅源"模式虽在技术上类似，但其面向的是重度信息消费者，门槛远高于本项目的"勾选预设平台"模式。

### 4.4 差异化定位

| 维度               | 竞品现状                   | 本方案                                     |
| ------------------ | -------------------------- | ------------------------------------------ |
| 平台组合           | 固定，用户不可改           | 用户从注册表勾选，偏好持久化                 |
| 布局               | 固定列数（按平台数硬编码） | 动态网格，自动适应平台数量                  |
| 默认展示           | 展示全部（信息过载）       | 默认 3 平台，可按需增加                     |
| 数据获取           | 多数聚合一次请求全部       | 动态路由按需获取，减少无用请求              |
| 偏好持久化         | 不支持                     | localStorage，零后端成本                    |

## 5. 技术可行性研究

### 5.1 平台注册表架构

核心思路：将平台定义从硬编码数组升级为**平台注册表**（Map/Record），后端和前端共享同一份元数据。

```typescript
// 平台注册表结构（后端定义，前端通过 API 获取元数据）
interface PlatformDescriptor {
  id:          string;
  name:        string;
  icon:        string;
  color:       string;
  description: string;
  enabled:     boolean;   // 是否默认启用
  fetch:       () => Promise<HotItem[]>;  // 后端内部，不暴露给前端
}
```

注册表示例：

| id         | name       | icon | color     | enabled | 说明                   |
| ---------- | ---------- | ---- | --------- | ------- | ---------------------- |
| `weibo`    | 微博热搜   | 🔥   | `#e6162d` | true    | 默认启用               |
| `zhihu`    | 知乎热榜   | 💡   | `#0066ff` | true    | 默认启用               |
| `bilibili` | B 站热搜   | 📺   | `#fb7299` | true    | 默认启用               |
| `baidu`    | 百度热搜   | 🔍   | `#3385ff` | false   | 后续接入，默认不启用    |
| `toutiao`  | 头条热榜   | 📰   | `#e13020` | false   | 后续接入，默认不启用    |

### 5.2 动态路由设计

后端 API 需从固定平台升级为接受平台参数：

| 路由                           | 说明                                           |
| ------------------------------ | ---------------------------------------------- |
| `GET /api/platforms`           | 返回平台注册表元数据（不含 fetch 函数）          |
| `GET /api/hot?platforms=a,b,c` | 按参数获取指定平台数据，缺省时使用默认启用平台    |

缓存键从固定的 `"hot"` 变为按平台组合生成，例如 `"hot:weibo,zhihu,bilibili"`，确保不同平台组合各自有独立的缓存。

### 5.3 现有 API 可用性验证

| 平台 | API 端点                                                    | 方法 | 认证需求       | 字段完整性 |
| ---- | ----------------------------------------------------------- | ---- | -------------- | ---------- |
| 微博 | `weibo.com/ajax/side/hotSearch`                             | GET  | UA + Referer   | 完整       |
| 知乎 | `zhihu.com/api/v3/feed/topstory/hot-lists/total?limit=50`   | GET  | UA             | 完整       |
| B 站 | `api.bilibili.com/x/web-interface/wbi/search/square?limit=50` | GET | 无             | 完整       |

### 5.4 实测发现与限制

#### 5.4.1 微博

- `word` 字段偶有 HTML 实体编码（`&amp;`），需解码
- `raw_hot` 为纯数字，量级差异大（数千至数千万）
- 对频繁请求敏感，7 分钟以上缓存间隔可避免限流

#### 5.4.2 知乎

- `target.url` 可能为相对路径，需补全 `https://www.zhihu.com` 前缀
- `detail_text` 为文本（如"1000 万热度"），后端需提取数字部分
- API 对 User-Agent 敏感，需模拟浏览器 UA
- 不返回 `rank` 字段，排名按数组索引生成

#### 5.4.3 B 站

- 热搜接口目前无需 wbi 签名，但 B 站大部分公开 API 已启用该机制，未来存在引入签名的可能
- `show_name`（展示文案）与 `keyword`（搜索词）可能不一致，URL 拼接优选 `keyword`
- `heat_score` 为纯数字，量级与微博不同

### 5.5 自适应布局方案

不同于固定 3 列的硬编码，采用 CSS Grid 的 `auto-fill` + `minmax` 实现自动适配：

```css
.grid {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(320px, 1fr));
  gap: 20px;
}
```

该方案在不同平台数量下的表现：

| 平台数 | 桌面端（>1000px） | 平板端（640–1000px） | 手机端（<640px） |
| ------ | ----------------- | -------------------- | ---------------- |
| 1      | 1 列              | 1 列                 | 1 列             |
| 2      | 2 列              | 2 列                 | 1 列             |
| 3      | 3 列              | 2 列                 | 1 列             |
| 4+     | auto-fill（最多约 3 列） | auto-fill      | 1 列             |

**优势**：无需针对不同平台数量编写媒体查询，CSS Grid 自动计算最优列数。每个卡片最小宽度 320px，保证内容可读性。

### 5.6 前端状态管理

```
localStorage["hot-site-platforms"] = "weibo,zhihu,bilibili"
                    ↓
          React state: selectedPlatforms
                    ↓
          fetch(`/api/hot?platforms=${selectedPlatforms.join(",")}`)
                    ↓
          渲染 PlatformCard × N（N = 选中平台数）
```

关键设计决策：

1. **localStorage 作为唯一真相源**：组件初始化时读取，用户变更时同步写入
2. **API 请求附带平台参数**：避免获取用户不关心的平台数据
3. **移除/添加平台时仅更新对应卡片**：利用 React key 机制实现最小化 DOM 更新

### 5.7 架构方案可行性结论

```
                  GET /api/platforms（元数据）
浏览器 ←────────────────────────────────  Express 后端
   │                                          │
   │  localStorage 读取选中平台                 │  PLATFORM_REGISTRY
   │  selectedPlatforms = [weibo, zhihu]       │  ├─ weibo → fetchWeibo()
   │                                          │  ├─ zhihu → fetchZhihu()
   │  GET /api/hot?platforms=weibo,zhihu       │  ├─ bilibili → fetchBilibili()
   │ ─────────────────────────────────────→    │  └─ ... (可扩展)
   │                                          │
   │  JSON 响应 { ok, data: Platform[] }       │  缓存键: "hot:weibo,zhihu"
   │ ←─────────────────────────────────────    │  TTL: 7 分钟
   │                                          │
   │  CSS Grid auto-fill 渲染 2 张卡片          │
   └──────────────────────────────────────────┘
```

**可行性结论**：平台注册表架构仅需将现有 `PLATFORMS` 数组改为 `Map`，动态路由接收查询参数，前端新增一个平台选择器组件。现有 fetch 函数无需修改，核心改动量可控，MVP 周期内可完成。

## 6. 风险评估

### 6.1 技术风险

| 风险                     | 概率 | 影响                   | 缓解措施                                                     |
| ------------------------ | ---- | ---------------------- | ------------------------------------------------------------ |
| 平台 API 变更或下线      | 中   | 该平台数据不可用       | `Promise.allSettled` 容错；该平台卡片显示错误提示，不影响其他平台 |
| IP 被限流或封禁          | 低   | 全部数据不可用         | 7 分钟缓存控制频率（每小时约 9 次/平台组合）；合理 UA          |
| 平台要求登录态           | 低   | 该平台不可用           | 定期监控 API 可用性；注册表中标记为不可用                       |
| B 站引入 wbi 签名        | 中   | B 站数据不可用         | 需实现 wbi 签名算法（已有开源实现）                             |
| 用户选择过多平台导致性能下降 | 低 | 页面加载变慢           | 并发请求 + 各平台独立缓存；后续可加虚拟滚动优化                 |
| 多用户共享同一缓存键     | 低   | 不同用户的选择互相干扰 | 缓存键按平台组合生成（如 `hot:weibo,zhihu`），不同组合独立缓存   |

### 6.2 法律合规风险

| 风险             | 概率 | 影响             | 缓解措施                                                     |
| ---------------- | ---- | ---------------- | ------------------------------------------------------------ |
| 内容版权争议     | 低   | 可能收到侵权通知 | 页脚声明数据来源及非商业用途；仅展示标题与链接，不复制内容正文 |
| 平台反爬条款     | 低   | 可能被平台屏蔽   | 调用频率远低于爬虫；不伪造、不绕过认证机制                     |

### 6.3 项目风险

| 风险               | 概率 | 影响             | 缓解措施                                 |
| ------------------ | ---- | ---------------- | ---------------------------------------- |
| 范围蔓延（不断增加新平台） | 中   | 开发周期失控 | 注册表模式天然限制：新增平台仅需添加一个 fetch 函数 |
| 热榜数据失去时效价值 | 低   | 产品无使用价值   | 缓存 TTL 上限 10 分钟                     |

## 7. 约束条件

| 约束类型   | 具体约束                                                         |
| ---------- | ---------------------------------------------------------------- |
| 数据来源   | 仅使用各平台公开 JSON API，不爬 HTML 页面，不伪造登录态             |
| 缓存策略   | 后端内存缓存，按平台组合生成缓存键，TTL 7 分钟                      |
| 部署要求   | 必须支持 HTTPS 公网访问，优先 Vercel（零配置、免费额度充足）        |
| MVP 周期   | 核心功能（默认 3 平台 + 自定义选择 + 动态布局）应在 3 小时内完成     |
| 技术栈限制 | 不引入数据库、SSR 框架、CSS 框架等重型依赖                          |
| 持久化     | 用户偏好仅存储于浏览器 localStorage，不做服务端存储                   |
| 安全要求   | 所有外链使用 `target="_blank" rel="noopener noreferrer"`           |
| 法律合规   | 页脚声明数据来源与非商业用途；不修改、不截留原始链接                  |

## 8. 研究结论

### 8.1 需求可行性

固定平台列表的聚合产品存在信息冗余、缺乏个性化、偏好无法持久化三大痛点。用户自定义平台组合功能填补了市场空白——经调研，7 款直接/间接竞品均无此能力。RSS 阅读器的订阅管理模式证明"用户主动管理信息来源"是一个被市场接受的行为模式。

### 8.2 策略定位

本项目采取"默认精简 + 用户扩展"的策略：首次访问默认展示微博、知乎、B 站三平台，用户可按需增减。平台注册表架构使得新增平台仅需添加一个 fetch 函数，后续迭代成本极低。

### 8.3 技术路径

MVP 技术实现路径清晰且风险可控：

```
平台注册表（PLATFORM_REGISTRY Map）
       ↓
动态路由（GET /api/hot?platforms=a,b）
       ↓
按平台组合缓存（cache key = "hot:a,b"）
       ↓
Promise.allSettled 并发请求
       ↓
React 前端渲染（PlatformSelector + 动态 Grid）
       ↓
localStorage 持久化用户选择
       ↓
Vercel 一键部署
```

### 8.4 下一步

基于本研究报告的结论，进入产品需求定义阶段，输出 `PRD.md`，明确平台选择器的交互细节、动态布局规则、API 参数规范及组件树结构。
